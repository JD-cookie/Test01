# Backlog

Feature and work requests that aren't built yet. This file is the project's ticket system: each item is one row, its history is this file's git history, and each ticket becomes one branch and one PR.

**Agents: pick up work with the `next-ticket` skill, [`.agents/skills/next-ticket/SKILL.md`](../../.agents/skills/next-ticket/SKILL.md).** It uses [`scripts/ticket.sh`](../../scripts/ticket.sh) to list the ready tickets and to claim one. To get an item ready to build, use the `refine-ticket` skill, [`.agents/skills/refine-ticket/SKILL.md`](../../.agents/skills/refine-ticket/SKILL.md). Claude Code, Codex, and opencode all find both as skills. Any other agent follows the same file: see "Backlog tickets" in [`AGENTS.md`](../../AGENTS.md#backlog-tickets).

## Statuses

| Status | Meaning | Who sets it |
|---|---|---|
| `idea` | A row, no design doc yet | Anyone |
| `designed` | Has a design doc, `docs/backlog/<slug>.md`, but it isn't ready to build | Anyone |
| `ready` | Has a **number** and a design doc `docs/backlog/NNNN-<slug>.md` that meets the [Definition of Ready](#definition-of-ready). Agents only pick up `ready` tickets, and only once every item in its "Blocked by: …" is built: until then it's **waiting** (see "Blocked items"). | **The user decides.** An agent may make the edit after the user approves, in a PR the user merges. |
| `in progress (claim …)` | Claimed by an agent. This status is only on the ticket's branch: it reaches `main` with the PR, which removes the row anyway. | `scripts/ticket.sh claim` |

## How it works

- **Adding an item:** add a row with status `idea`. Leave the `#` column empty. A design doc is optional at first.
- **Designing an item:** write `docs/backlog/<slug>.md`, for example `password-reset.md`, link the title to it, and set the status to `designed`. Use a ticket doc's sections (see [../README.md](../README.md#writing-a-feature-doc)), and fill in as much as is known.
- **Refining it:** run the `refine-ticket` skill on the item. It checks the doc against the [Definition of Ready](#definition-of-ready), asks the user about the open decisions, proposes a split if it's too big, and gets an independent review. It records all of that in the doc's **Readiness review** section, then asks the user to approve.
- **Marking it ready (the user decides):** give it the next free number, four digits, zero-padded (`0007`). That is one more than the highest number in this table, in [`docs/features/`](../features/) and [`docs/tickets/`](../tickets/README.md), and in the names of the `NNNN-*` and `ready-NNNN` branches on `origin`. Rename its doc to `NNNN-<slug>.md`, check that it meets the Definition of Ready, and set the status to `ready`, in one PR on a branch named `ready-NNNN`. Push that branch create-only (`git push --force-with-lease=refs/heads/ready-NNNN: …`): if it already exists, another ready PR holds the number, so take the next one. Each number then reaches `main` only once, so two agents working in parallel can never take the same one. The user can do this by hand, or approve it in `refine-ticket`, which does it. The ticket's branch is named `NNNN-<slug>`. An item can be marked `ready` before what blocks it is built: it keeps its "Blocked by: …" and waits (see "Blocked items").
- **Claiming it (an agent):** `scripts/ticket.sh claim next <agent-name>` claims the first free `ready` ticket, and `claim NNNN-<slug>` claims a named one. Whoever creates the ticket's branch on `origin` first holds the claim, and everyone else is turned away. No merge is needed. To see what's free: `scripts/ticket.sh list`. The claim rules, every command's output, and the exit codes are in the ticket system's spec, [`0008-ticket-system.md`](../features/0008-ticket-system.md).
- **Building it,** on its branch, in its PR (see "Writing a feature doc" in [../README.md](../README.md#writing-a-feature-doc) for the two kinds of doc):
  1. **The ticket doc:** `git mv docs/backlog/NNNN-<slug>.md docs/tickets/NNNN-<slug>.md`, and update its spec sections to match what was built. The version that was marked ready stays in git, in the ready PR. Its status line says built, with the date. After the status line, a **Spec docs changed** line links each spec doc it changed. It gets a **Delivery and review** section, which also says what changed from the ready version and why.
  2. **Make its links stable:** drop the section (`#…`) from each link to a spec doc, and turn each link to anything else outside `docs/tickets/` into a permalink, or into plain text for a file the PR adds (see "Stable links" in [../README.md](../README.md#writing-a-feature-doc)).
  3. **The spec:** for a new capability, write `docs/features/NNNN-<slug>.md`, with the ticket's number, from the ticket's spec sections as built, and add it to the Features table in [../README.md](../README.md#features). For a change to an existing capability, edit its doc in place. Operational changes go in [`docs/devops.md`](../devops.md). A ticket can do both.
  4. **Changes lists:** each spec doc it changed gets a line at the end of its **Changes** section: `- NNNN: <title> ([ticket](<path>))`, with the path relative to the spec doc: `../tickets/NNNN-<slug>.md` from `docs/features/`, and `tickets/NNNN-<slug>.md` from `docs/README.md` and `docs/devops.md`.
  5. **The index:** add a row to [`docs/tickets/README.md`](../tickets/README.md): `| NNNN | [<title>](NNNN-<slug>.md) | #<PR> | <spec docs changed, linked> |`. The PR number is known once the PR is open: add it in a commit after opening it.
  6. Delete its row here, and fix links to the old path everywhere outside `docs/tickets/`.

  A ticket doc in `docs/tickets/` is frozen once its PR merges, and a spec doc is never renamed or deleted once the PR that adds it has merged.
- **Releasing a claim** (only the user): delete the ticket's branch on `origin`. The ticket is free again, because on `main` it still says `ready`.
- **Dropping an item:** delete the row and its design doc, and note why in the commit message.
- **Order:** rows are roughly in priority order, highest first. Agents take the first free `ready` ticket unless told otherwise. Reorder freely.
- **Blocked items:** an item that can't start until others are built begins its Notes with "Blocked by: …", naming those items by title, separated by `; `, and ending at the first `. ` (the rest of the Notes is free text). It can still be marked `ready` once its design is approved. A `ready` ticket with an item there that isn't built is **waiting**: `scripts/ticket.sh list` shows it as `waiting on: <title>; …`, `claim next` skips it, and `claim NNNN-<slug>` refuses it. Once each one is built, the same row is free to claim, with no edit. A title that has no row and isn't listed as built, an empty entry, or a Notes cell that starts "Blocked by" spelled another way (`Blocked By: A`), counts as not built, so the ticket waits until the row is fixed. An item is built when its row is gone from this table and it's listed in [`docs/tickets/README.md`](../tickets/README.md), or, for features built before the backlog (0001 and 0002), in the Features table of [../README.md](../README.md#features).

## Definition of Ready

A ticket is ready to build when its design doc meets every item that applies. The `refine-ticket` skill checks each one, and reviewers can use the same list.

1. **Purpose:** the summary says what problem it solves, for whom, and what changes for users or operators. It also says what doesn't change. For a change to existing behavior, it states the current behavior and the behavior wanted.
2. **Needed:** it isn't already built, and it doesn't repeat or contradict another backlog item or something dropped before.
3. **Scope:** what's in and what's out is explicit, including an out-of-scope list for anything nearby that a builder might be tempted to include. Anything left for later is a separate backlog row or a known gap, not a vague "maybe".
4. **Fits one PR:** one branch, one reviewable PR, one behavior change that can ship on its own, and small enough for one agent session. A rough guide: if the implementation map touches more than about three areas (app, server, CI, infra), or the acceptance checks fall into groups that could each ship alone, split it.
5. **Enough information to build it without asking:**
   - every endpoint, table, setting, message, and error code it adds or changes, with exact values
   - the files in the implementation map exist, or are clearly new files
   - links to the feature docs it changes
   - the backlog items that block it, if any
6. **Steps only the user can do** are listed as tasks for the user: settings, secrets, rulesets, accounts, and anything else an agent can't do. For each one, the doc says when it has to happen (before the PR is merged, or after it ships) and how the builder can check that it's done.
7. **Acceptance checks:** each one is a concrete scenario, with an input or setup and an observable expected result. They cover the failure paths and edge cases, not just the happy path. No check uses words like "works", "fast", or "secure" without saying what's measured. Each check also says:
   - **where it's tested:** the highest existing entry point that can test it, such as the HTTP API through Fastify's `inject`, the claim script run against a scratch repo, a CI job, or the app on a device
   - **what shows it passed:** something other than the builder's word, such as a test, a CI job's result, or a command and its output
8. **The project's rules** ([`AGENTS.md`](../../AGENTS.md#rules)) are addressed where they apply. For example:
   - attempt limits (rule 1)
   - more than one instance (rule 2): shared state, and migrations or jobs run by several instances at once
   - docs updated in the same PR (rule 3)
   - versions left to release-please (rule 4)
   - workflow permissions and triggers (rule 5)
9. **Security and failure modes:** who can trigger it, what happens when a dependency is down, and what's logged. It also lists the known gaps.
10. **No open questions.** Choices are written down in "Decisions made for this ticket", with the reason for each.
